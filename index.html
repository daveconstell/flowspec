Specs that describe the flow, not the framework.

FlowSpec is a declarative language for AI-driven acceptance testing. One file per feature, one case per path through it — happy and sad alike. Any engine, from AI browser agents to Playwright, decides how to run them.

Declarative

Describe what should happen, never how it happens.

One flow per file

A file is a feature journey. No container layer, no nesting to navigate.

Cases are paths

Independent scenarios through the flow — and every one, sad paths included, is expected to pass.

Semantic

Stable component names via a data attribute you choose — never CSS or XPath.

Readable by both

A QA engineer writes one without programming; an LLM runs one without prompting.

Engine agnostic

The same flow runs on AI agents, Playwright, Selenium, or mobile.

Getting started

Four steps to your first flow

FlowSpec is a specification, not a test runner. You annotate your UI, author a flow file per journey, and point an execution engine at it — the engine decides how to drive the browser.

First, install the skill

Optional but recommended: one file, no dependencies. Drop SKILL.md into your agent's skills directory and every step below becomes a /flowspec command. Restart the session, then run /flowspec to confirm it loaded. 

# download it straight in
mkdir -p ~/.claude/skills/flowspec
curl -fsSL https://raw.githubusercontent.com/\
daveconstell/flowspec/main/public/SKILL.md \
  -o ~/.claude/skills/flowspec/SKILL.md

# …or clone and run the installer
git clone https://github.com/daveconstell/flowspec.git
./flowspec/install-skill.sh              # global
./flowspec/install-skill.sh /path/to/app # project

Skill commands

Eight commands. Anything else — including no args — prints help

/flowspec help
The command list plus the setup state — config, the flows you have, the effective target attribute, and whether any testing tooling is actually connected. Changes nothing.
/flowspec init
Detect baseUrl and targetAttribute from the repo, write .flowspec.json, create .flowspec/. Doesn't author a flow — which feature comes first is your call.
/flowspec run [file] [case]
Find the browser tooling — Chrome DevTools MCP, Playwright, Cypress — drive the paths, write flowspec-results/, and report every case with expected vs. actual. No file runs everything; naming a case runs just that one. --url overrides the origin, headless unless --headed.
/flowspec flow:new
Create a flow. Proposes the paths the feature offers — the refusals included — asks which you want, then walks each one with you in the browser (or derives it from the source) and writes them as cases in one _flow.json, annotating components as it goes.
/flowspec flow:set
Update a flow's own fields — name, description, variables, setup, cleanup. Editing setup touches every case in the file, so it says which and confirms first.
/flowspec case:new
Add a path to a flow — and it always asks which flow first, even when only one exists. A case in the wrong file tests the wrong feature under the wrong setup. Then it walks the path with you in the browser, or derives it from the source.
/flowspec case:set
Update a case. Asks which flow, then which case, then says what it's changing before touching it — and never relaxes an assertion just to make a run go green.
/flowspec mermaid [file]
Render a flow as a diagram, derived from the file: one shared setup, one branch per case, one outcome each. A fan, not a chain — nothing connects two cases, because nothing does.

Two standing guards. Nothing claims to run without browser tooling actually connected — a run that can't happen is never reported as a pass. And any precondition, credential, or seeded record a flow needs is asked for, never invented or left as a placeholder.

Or walk the path together

With a browser MCP connected and the app up, flow:new and case:new don't guess from the source — they drive the real thing. The agent runs the flow's setup, tells you where it landed and which components it can reach by name, and asks what the user does next. Each plain answer becomes one step, executed for real.

At the end it asks the acceptance criteria — those become the assertions. You never see a selector and never write JSON.

It won't record what it can't replay: use a control with no target attribute and the walk stops to name it first. That's the difference between this and a click recorder — what comes out is a portable FlowSpec any engine can run, not a script bound to today's markup.

  1. 1

    Annotate your components

    Add a data attribute to every element a test needs to reach, naming components by role rather than appearance so the name survives a redesign. Already using data-testid or a house convention? Declare it as targetAttribute and change no markup at all. And if the configured attribute is absent from the page entirely, engines detect the convention the page actually uses, run with it, and flag the config mismatch — rather than failing every step. 

    <!-- role, not appearance -->
<form data-constell="quote-form">
  <input data-constell="quote-email" />
  <button data-constell="quote-submit">
    Request a quote
  </button>
</form>

// .flowspec.json — project settings,
// including the attribute you already use
{
  "baseUrl": "http://localhost:5173",
  "targetAttribute": "data-testid"
}
  2. 2

    Write the flows

    One feature per file in .flowspec/, with project settings in .flowspec.json. The file is the flow, so there's no wrapper to write and its name is its id. Inside it, one case per path a user can take — the steps that reproduce the path, then what must be true at the end of it. Never how to click it. With the skill installed, /flowspec init detects those settings from your repo and /flowspec flow:new drafts one, a case per path.

    Cases are siblings, not a chain: each starts from the state setup establishes, all of them run, and a sad path passes by asserting the refusal shows up. 

    // .flowspec/login_flow.json
{
  "spec": "1.0",
  "name": "Login",
  // runs before each case, so paths
  // can't contaminate each other
  "setup": [
    { "action": "clear-storage" },
    { "action": "navigate", "url": "/login" }
  ],
  "cases": [{
    "id": "valid-credentials", /* … */
  }, {
    "id": "inactive-account",
    "steps": [
      { "action": "fill",
        "target": "login-form",
        "values": { "login-email": "{{dormant}}" } },
      { "action": "click",
        "target": "login-submit" }
    ],
    "assertions": [
      { "type": "text",
        "target": "login-error",
        "expected": "account is not active",
        "description": "Explains why" }
    ]
  }, {
    "id": "invalid-credentials", /* … */
  }]
}
  3. 3

    Point an engine at it

    There is no official runner yet — FlowSpec 1.0 defines the contract, and engines implement it. Give an AI coding agent the SKILL.md and your flow file and it can execute the journey directly — installed as a skill it answers to /flowspec run — or write a thin adapter that maps actions onto Playwright. 

    // a Playwright adapter is ~40 lines:
// resolve the target…
const attr = flow.targetAttribute ?? 'data-constell'
page.locator(`[${attr}="${step.target}"]`)

# …then dispatch on the action
switch (step.action) {
  case 'click':  await el.click()
  case 'fill':   await el.fill(value)
  case 'submit': await el.press('Enter')
}
  4. 4

    Consume the results

    Every conformant engine writes the same layout, so your CI config outlives your choice of engine. Publish the directory as a build artifact and gate the pipeline on the exit code. 

    # .github/workflows/acceptance.yml
- run: your-engine  # discovers .flowspec/**/*.json

- uses: actions/upload-artifact@v4
  if: always()
  with:
    name: acceptance-evidence
    path: flowspec-results/
§13 – §14

Results are part of the specification

A test format is only portable if its output is too. FlowSpec defines not just the shape of a result but where it lands — so a CI pipeline, dashboard, or flake tracker works against any conformant engine instead of being rewritten for each one.

flowspec-results/ 
flowspec-results/
├── report.json            # run summary
└── login_flow/            # one dir per flow
    ├── report.json        # flow → cases
    ├── report.xml         # optional JUnit, for CI
    └── evidence/
        └── inactive-account/
            ├── screenshot.png
            ├── dom.html
            └── console.log

Self-contained bundles

Evidence is referenced by relative path, so the results directory zips, uploads as a CI artifact, or attaches to a pull request with every link intact.

Mirrors your sources

A flow's id is its filename, and results nest the same way, so .flowspec/admin/invite_user_flow.json reports to admin/invite_user_flow/ — collision-free, because file paths are.

Stable identity

Every case has a fully-qualified id — flow-id/case-id — that holds across runs, so flakiness can be tracked over time.

Readable failures

Names and descriptions carry into the report, so a failure reads “The confirmation banner appears — failed”, not visible: success-message.

exit 0

Every flow passed.

exit 1

A flow failed — a product bug.

exit 2

A flow errored or a flow file was invalid — a broken run.
