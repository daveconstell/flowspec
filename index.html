Specs that describe the flow, not the framework.

FlowSpec is a declarative language for AI-driven acceptance testing. Describe user journeys and expected behavior — any engine, from AI browser agents to Playwright, decides how to run them.

Declarative

Describe what should happen, never how it happens.

Semantic

Stable component names via a data attribute you choose — never CSS or XPath.

Human readable

QA engineers read and write specs without programming knowledge.

AI readable

An LLM executes a FlowSpec without additional prompting.

Engine agnostic

The same document runs on AI agents, Playwright, Selenium, or mobile.

Versioned

Every document declares the spec version it targets.

Getting started

Four steps to your first flow

FlowSpec is a specification, not a test runner. You annotate your UI, author a document, and point an execution engine at it — the engine decides how to drive the browser.

First, install the skill

Optional but recommended: one file, no dependencies. Drop SKILL.md into your agent's skills directory and the steps below become /flowspec commands — init, new, review, run. Restart the session, then run /flowspec to confirm it loaded. 

# download it straight in
mkdir -p ~/.claude/skills/flowspec
curl -fsSL https://raw.githubusercontent.com/\
daveconstell/flowspec/main/public/SKILL.md \
  -o ~/.claude/skills/flowspec/SKILL.md

# …or clone and run the installer
git clone https://github.com/daveconstell/flowspec.git
./flowspec/install-skill.sh              # global
./flowspec/install-skill.sh /path/to/app # project
  1. 1

    Annotate your components

    Add a data attribute to every element a test needs to reach, naming components by role rather than appearance so the name survives a redesign. Already using data-testid or a house convention? Declare it as targetAttribute and change no markup at all. 

    <!-- role, not appearance -->
<form data-constell="quote-form">
  <input data-constell="quote-email" />
  <button data-constell="quote-submit">
    Request a quote
  </button>
</form>

// .flowspec.json — project settings,
// including the attribute you already use
{
  "baseUrl": "http://localhost:5173",
  "targetAttribute": "data-testid"
}
  2. 2

    Write the documents

    Keep one document per page or area in .flowspec/, with project settings in .flowspec.json. Describe each journey as flows and cases — what the user does and what should be true afterwards. Never how to click it. With the skill installed, /flowspec init detects those settings from your repo and /flowspec new <page> drafts the document. 

    // .flowspec/venue-landing.json
{
  "spec": "1.0",
  "name": "Quote requests",
  "flows": [{
    "id": "request-quote",
    // each flow starts on its own page
    "setup": [
      { "action": "navigate", "url": "/birthday" }
    ],
    "cases": [{
      "id": "submit",
      "steps": [
        { "action": "click",
          "target": "quote-submit" }
      ],
      "assertions": [
        { "type": "visible",
          "target": "success-message",
          "description": "Confirmation shows" }
      ]
    }]
  }]
}
  3. 3

    Point an engine at it

    There is no official runner yet — FlowSpec 1.0 defines the contract, and engines implement it. Give an AI coding agent the SKILL.md and your document and it can execute the journey directly — installed as a skill it answers to /flowspec run — or write a thin adapter that maps actions onto Playwright. 

    // a Playwright adapter is ~40 lines:
// resolve the target…
const attr = doc.targetAttribute ?? 'data-constell'
page.locator(`[${attr}="${step.target}"]`)

# …then dispatch on the action
switch (step.action) {
  case 'click':  await el.click()
  case 'fill':   await el.fill(value)
  case 'submit': await el.press('Enter')
}
  4. 4

    Consume the results

    Every conformant engine writes the same layout, so your CI config outlives your choice of engine. Publish the directory as a build artifact and gate the pipeline on the exit code. 

    # .github/workflows/acceptance.yml
- run: your-engine  # discovers .flowspec/**/*.json

- uses: actions/upload-artifact@v4
  if: always()
  with:
    name: acceptance-evidence
    path: flowspec-results/
§13 – §14

Results are part of the specification

A test format is only portable if its output is too. FlowSpec defines not just the shape of a result but where it lands — so a CI pipeline, dashboard, or flake tracker works against any conformant engine instead of being rewritten for each one.

flowspec-results/ 
flowspec-results/
├── report.json        # the full result tree
├── report.xml         # optional JUnit, for CI
└── evidence/
    └── request-quote/
        └── submit/
            ├── screenshot.png
            ├── dom.html
            └── console.log

Self-contained bundles

Evidence is referenced by relative path, so the results directory zips, uploads as a CI artifact, or attaches to a pull request with every link intact.

Mirrors your sources

Split a large site across many documents in .flowspec/ and results nest the same way, so admin/users.json reports to admin/users/ — collision-free, because file paths are.

Stable identity

Every case has a fully-qualified id — flow-id/case-id — that holds across runs, so flakiness can be tracked over time.

Readable failures

Names and descriptions carry into the report, so a failure reads “The confirmation banner appears — failed”, not visible: success-message.

exit 0

Every flow passed.

exit 1

A flow failed — a product bug.

exit 2

A flow errored or the document was invalid — a broken run.
