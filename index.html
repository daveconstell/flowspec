Specs that describe the flow, not the framework.

FlowSpec is a declarative language for AI-driven acceptance testing. Describe user journeys and expected behavior — any engine, from AI browser agents to Playwright, decides how to run them.

Declarative

Describe what should happen, never how it happens.

Semantic

Stable component names via data-constell — never CSS or XPath.

Human readable

QA engineers read and write specs without programming knowledge.

AI readable

An LLM executes a FlowSpec without additional prompting.

Engine agnostic

The same document runs on AI agents, Playwright, Selenium, or mobile.

Versioned

Every document declares the spec version it targets.

Getting started

Four steps to your first flow

FlowSpec is a specification, not a test runner. You annotate your UI, author a document, and point an execution engine at it — the engine decides how to drive the browser.

  1. 1

    Annotate your components

    Add a data-constell attribute to every element a test needs to reach. Name components by role, not appearance, so the name survives a redesign. This is the only change FlowSpec asks of your application. 

    <!-- role, not appearance -->
<form data-constell="quote-form">
  <input data-constell="quote-email" />
  <button data-constell="quote-submit">
    Request a quote
  </button>
</form>
  2. 2

    Write the document

    Create a .flowspec.json file. Describe the journey as flows and cases — what the user does and what should be true afterwards. Never how to click it. 

    {
  "spec": "1.0",
  "name": "Quote requests",
  "setup": [
    { "action": "navigate", "url": "/birthday" }
  ],
  "flows": [{
    "id": "request-quote",
    "cases": [{
      "id": "submit",
      "steps": [
        { "action": "click",
          "target": "quote-submit" }
      ],
      "assertions": [
        { "type": "visible",
          "target": "success-message",
          "description": "Confirmation shows" }
      ]
    }]
  }]
}
  3. 3

    Point an engine at it

    There is no official runner yet — FlowSpec 1.0 defines the contract, and engines implement it. Give an AI coding agent the SKILL.md and your document and it can execute the journey directly, or write a thin adapter that maps actions onto Playwright. 

    # a Playwright adapter is ~40 lines:
# resolve the target…
page.locator(`[data-constell="${step.target}"]`)

# …then dispatch on the action
switch (step.action) {
  case 'click':  await el.click()
  case 'fill':   await el.fill(value)
  case 'submit': await el.press('Enter')
}
  4. 4

    Consume the results

    Every conformant engine writes the same layout, so your CI config outlives your choice of engine. Publish the directory as a build artifact and gate the pipeline on the exit code. 

    # .github/workflows/acceptance.yml
- run: your-engine quote.flowspec.json

- uses: actions/upload-artifact@v4
  if: always()
  with:
    name: acceptance-evidence
    path: flowspec-results/
§13 – §14

Results are part of the specification

A test format is only portable if its output is too. FlowSpec defines not just the shape of a result but where it lands — so a CI pipeline, dashboard, or flake tracker works against any conformant engine instead of being rewritten for each one.

flowspec-results/ 
flowspec-results/
├── report.json        # the full result tree
├── report.xml         # optional JUnit, for CI
└── evidence/
    └── request-quote/
        └── submit/
            ├── screenshot.png
            ├── dom.html
            └── console.log

Self-contained bundles

Evidence is referenced by relative path, so the results directory zips, uploads as a CI artifact, or attaches to a pull request with every link intact.

Stable identity

Every case has a fully-qualified id — flow-id/case-id — that holds across runs, so flakiness can be tracked over time.

Readable failures

Names and descriptions carry into the report, so a failure reads “The confirmation banner appears — failed”, not visible: success-message.

exit 0

Every flow passed.

exit 1

A flow failed — a product bug.

exit 2

A flow errored or the document was invalid — a broken run.
